# ShelfBot 구현 계획서 (상세)

자율주행·모방학습 기반 무인 상품 진열 시스템.
기획서: `ShelfBot_프로젝트_기획서.docx` / 팀: 이기문(팀장), 강성준

---

## 0. 한 줄 요약

pinky 위에 간식을 올리고 웹 UI에서 ▶시작을 누르면 —
pinky가 SLAM 내비게이션으로 진열대 앞까지 주행하고, 아루코 마커로 정밀 도킹한 뒤,
soarm101 로봇팔이 모방학습(ACT) 정책으로 상품을 집어 **상품별 지정 칸**에 진열한다.

## 1. 시스템 구성

### 1.1 하드웨어

| # | 장비 | 역할 | 연결/비고 |
|---|---|---|---|
| 1 | pinky pro | 상품 운반. SLAM·Nav2 자율주행 — 공식 패키지(pinky_bringup, pinky_navigation)를 온보드에서 그대로 실행 | WiFi (ROS2 DDS) |
| 2 | soarm101 (SO-ARM101) | 상품 파지·진열. LeRobot 프레임워크 | 노트북 USB 직결 |
| 3 | 핸드캠 | 로봇팔 손목 시점. **정책 입력 전용** | 노트북 USB |
| 4 | 탑뷰 캠 | 부스 전체(핑키·로봇팔·진열대). **정책 입력 + 아루코 도킹 검출 + 웹 스트림** 3역 | 노트북 USB. 위치 절대 고정 |
| 5 | 노트북 | orchestrator·도킹·정책 추론·웹 UI — 우리가 짜는 코드 전부 | Ubuntu 24.04, ROS2 Jazzy |
| 6 | 5090 서버 | ACT 학습 전용 | **torch 2.7+ / CUDA 12.8+ 필수** (Blackwell) |
| 7 | 부스 | 진열대 모형(3칸+), pinky 정차 마킹, 상품 받침, 고정 조명 | 3장 참조 |

### 1.2 네트워크·환경

- 노트북·pinky 동일 WiFi, **동일 `ROS_DOMAIN_ID`** (예: 42). 노트북 `~/.bashrc`와 pinky 온보드 모두 설정
- RMW는 pinky 공식 문서 기본값을 따름. 노트북↔pinky 토픽 통신은 `ros2 topic hz /scan`으로 최초 1회 검증
- 시간 동기화: pinky·노트북 NTP 확인 (`timedatectl`) — TF 타임스탬프 어긋나면 Nav2 경고 발생
- 노트북 파이썬 환경 2개 분리:
  - `ros2` 시스템 파이썬: orchestrator, docking, web (rclpy 의존)
  - `lerobot` conda/venv: 녹화·추론 (torch 의존, ROS와 격리)
  - 두 환경의 경계는 프로세스 경계 = orchestrator가 lerobot 추론을 **서브프로세스로 실행**

### 1.3 소프트웨어 구조

```
shelfbot/
├── ShelfBot_프로젝트_기획서.docx
├── 구현계획서.md
├── config/
│   ├── booth.yaml          # goal pose, 아루코 정위치 pose, 도킹 게인/임계값, 칸 매핑
│   └── cameras.yaml        # 캠 장치경로/해상도/fps (핸드캠·탑뷰 udev 심볼릭 링크 권장)
├── orchestrator/
│   ├── orchestrator_node.py  # 상태머신 rclpy 노드 (메인)
│   └── nav_client.py         # Nav2 액션 클라이언트 래퍼
├── docking/
│   ├── aruco_docking.py      # 아루코 검출 + cmd_vel P제어
│   └── calibrate_camera.py   # 탑뷰 캠 내부 파라미터 캘리브레이션 (체스보드)
├── arm/
│   ├── record.sh             # lerobot 녹화 래퍼 (에피소드 카운트·상품 라벨)

└── web/
    ├── server.py             # FastAPI: REST + WebSocket + MJPEG (orchestrator와 동일 프로세스)
    └── static/index.html     # UI 한 장 (외부 프레임워크 없음)
```

## 2. ROS2 인터페이스

| 이름 | 타입 | 방향 (노트북 기준) | 용도 |
|---|---|---|---|
| `/navigate_to_pose` | nav2_msgs/action/NavigateToPose | 클라이언트 → pinky | 진열대 앞 goal 전송, 결과 수신 |
| `/cmd_vel` | geometry_msgs/Twist | 퍼블리시 → pinky | 도킹 미세 보정 (Nav2 종료 후에만) |
| `/map` | nav_msgs/OccupancyGrid | 구독 | 웹 지도 렌더 (래치, 1회) |
| `/amcl_pose` (또는 pinky pose 토픽) | PoseWithCovarianceStamped | 구독 | 웹 지도의 로봇 위치 |
| `/plan` | nav_msgs/Path | 구독 | 웹 지도의 경로 표시 |
| pinky 카메라 이미지 토픽 | sensor_msgs/Image 또는 CompressedImage | 구독 | 웹 스트림 (pinky 문서에서 토픽명 확인 후 config에 기록) |

> 확인 필요(TBD): pinky pose·카메라 토픽 정확한 이름 — 부스 세팅 주에 `ros2 topic list`로 확정하고 `config/booth.yaml`에 기록.

## 3. 부스 세팅 절차 (순서 엄수 — 이 순서가 곧 데이터 유효성)

1. **배치·고정**: 진열대, 로봇팔 베이스, 탑뷰 캠을 클램프/볼트로 완전 고정. 고정 완료 상태를 사진으로 기록(재현용)
2. **조명 고정**: 스탠드 조명, 자연광 차단(창가 회피/커튼). 데이터 수집일과 시연일 조명 동일 유지
3. **정차 마킹**: 진열대 앞 pinky 목표 정차 지점을 바닥 테이프로 마킹. 로봇팔 작업 반경(파지 지점까지 여유 확보) 안인지 soarm101을 수동으로 뻗어 확인
4. **상품 받침 제작**: pinky 상판에 바형 간식을 **세워** 꽂는 홈/받침. 누운 바는 그리퍼로 파지 불가. 그리퍼 최대 개구와 상품 두께 실측 대조
5. **아루코 마커 부착**: pinky 상판에 마커 1장 (권장: DICT_4X4_50, id=0, 한 변 50~80mm — 탑뷰 화각에서 최소 30px 이상으로 보이는 크기). 평평하게, 로봇팔·상품에 가리지 않는 위치
6. **SLAM 지도 재작성**: 부스 완성 상태에서 pinky SLAM toolbox로 지도 신규 작성 → 저장. 기존 지도 폐기
7. **goal 좌표 저장**: RViz에서 마킹 지점의 map 좌표(x, y, yaw) 확인 → `config/booth.yaml`
8. **탑뷰 캠 캘리브레이션**: 체스보드로 내부 파라미터(K, dist) 산출 → 저장 (`calibrate_camera.py`)
9. **정위치 pose 실측**: pinky를 마킹 지점에 수동으로 정확히 배치 → 탑뷰 캠 아루코 pose(x, y, yaw — 이미지/카메라 좌표계 그대로) 기록 → `config/booth.yaml`의 `dock_target_pose`. 월드 좌표 변환 불필요 — "이 pose로 보이면 정위치" 방식
10. **주행+도킹 반복 테스트**: §5·§6 완료 후 20회 반복, 잔여 오차 실측

**변경 = 재촬영 원칙**: 3~9 확정 후에만 데이터 녹화 시작. 카메라·진열대·조명이 1cm라도 움직이면 그 시점 이후 데이터만 유효.

## 4. Orchestrator — 상태머신 상세

### 4.1 상태 정의

```
READY ──/start──▶ NAVIGATING ──도착──▶ DOCKING ──정렬──▶ PLACING ──성공──▶ DONE ──/reset──▶ READY
                     │실패/타임아웃        │실패/타임아웃      │실패/타임아웃
                     └────────────────────┴──────────────────┴──▶ FAILED(사유) ──/retry──▶ (실패한 단계부터 재시도)
```

| 상태 | 진입 동작 | 완료 조건 | 타임아웃 | 실패 처리 |
|---|---|---|---|---|
| READY | 대기. 상태 브로드캐스트 | `POST /start` | — | — |
| NAVIGATING | `NavigateToPose` goal 전송 (booth.yaml의 goal pose) | 액션 결과 SUCCEEDED | 120s | goal cancel → FAILED("nav_timeout"/"nav_aborted") |
| DOCKING | aruco_docking 제어 루프 시작 | 위치 오차 ≤ 15mm AND yaw 오차 ≤ 3° 가 연속 10프레임 유지 | 30s | cmd_vel 정지 → FAILED("dock_timeout"/"marker_lost") |
| PLACING | `run_policy.py` 서브프로세스 실행 (환경: lerobot venv) | 종료코드 0 | 90s | 프로세스 kill → 로봇팔 홈 복귀 명령 → FAILED("place_timeout"/"place_failed") |
| DONE | 사이클 로그 기록(각 단계 소요 시간, 총 시간), (선택) 시작점 복귀 goal | `/reset` | — | — |
| FAILED | 사유·단계 기록, 모든 구동 정지 | `/retry`(해당 단계부터) 또는 `/reset` | — | — |

### 4.2 구현 규칙

- rclpy 노드 1개 + FastAPI를 **같은 프로세스**에서 실행 (uvicorn을 스레드로, rclpy spin을 메인으로 — 또는 그 역). 프로세스 2개로 쪼개지 않는다
- 상태 전이마다: 타임스탬프 로그 파일(`logs/cycle_YYYYMMDD_HHMMSS.jsonl`) + WebSocket 브로드캐스트
- PLACING 중 비상 정지: 웹 UI ■정지 버튼 → 서브프로세스 SIGTERM → 로봇팔 토크 해제 전 홈 복귀
- 사이클 로그는 성공 기준 측정의 원자료 — 20회 시행 통계를 여기서 뽑는다

## 5. 아루코 정밀 도킹 상세

### 5.1 원리

Nav2는 ±수 cm 오차로 도착한다. 모방학습 정책은 학습 시 본 상대 위치에 민감하므로, 탑뷰 캠(고정)으로 pinky 상판 마커를 보고 "정위치에서 보이던 pose"와의 차이를 없앤다. 월드 좌표 변환 없이 **이미지 상 pose 차이 → cmd_vel** 직결.

### 5.2 알고리즘 (제어 루프 ~15Hz)

```
매 프레임:
  1. 탑뷰 프레임 취득 (frame hub 경유, §7.2)
  2. cv2.aruco 검출 (DICT_4X4_50) → 마커 코너 → solvePnP → (x, y, yaw)
  3. 오차 e = dock_target_pose - 현재 pose
  4. 미검출 프레임 연속 15개(≈1s) → marker_lost 실패
  5. cmd_vel 퍼블리시:
       linear.x  = clamp(Kp_lin * e_forward, -0.05, 0.05)   # m/s
       angular.z = clamp(Kp_ang * e_yaw,     -0.3,  0.3)    # rad/s
     (pinky는 차동구동 — 횡오차는 yaw를 틀어 전/후진으로 수렴시키는 2단계 접근)
  6. |e_pos| ≤ 15mm AND |e_yaw| ≤ 3° 연속 10프레임 → 정지(cmd_vel 0) → 성공
```

- 초기 게인: Kp_lin=0.5, Kp_ang=1.0에서 시작해 현장 튜닝. 값·임계값 전부 `booth.yaml`
- 안전: cmd_vel 상한 고정(위 clamp), 루프 종료 시 반드시 0 퍼블리시 (예외 포함 finally)
- 검증: 도킹 20회 반복 → 최종 오차 분포 기록. **이 잔여 오차 범위가 §6 녹화 시 pinky 위치 다양화 범위가 된다**

## 6. 모방학습 — 데이터·학습·추론

### 6.1 태스크 정의

- 단일 태스크: "pinky 위 상품을 파지하여 **상품에 해당하는 칸**에 진열 후 홈 자세 복귀"
- 에피소드 구조 통일: **홈 자세 시작 → 접근 → 파지 → 이동 → 진열 → 홈 복귀 → 종료**. 시작·끝 자세가 매번 동일해야 학습 안정
- 상품: 스니커즈·킷캣·자유시간 등 색상·모양이 뚜렷이 다른 간식 3종. **녹화 시작 전 확정** (상품 변경 = 해당 상품 전체 재촬영·재학습)
- 칸 매핑 고정 (예: 스니커즈→1칸, 킷캣→2칸, 자유시간→3칸), `booth.yaml`에 기록. 칸 간격 최대 확보 + 칸별 색 테이프 단서

### 6.2 관측·행동 공간

| 항목 | 내용 |
|---|---|
| 관측 | 핸드캠 + 탑뷰 캠 (각 640×480 @30fps), soarm101 관절 상태 |
| 행동 | soarm101 관절 목표치 (LeRobot 표준) |
| 사전 확인 | 파지 직전 프레임에서 핸드캠에 상품이 크고 선명하게 보이는 각도인지 — 안 보이면 캠 마운트 조정 후 시작 |

### 6.3 녹화 규칙

1. 상품당 **50 에피소드 이상** (3종 = 150+), 상품별 개수 균형 유지
2. 상품을 **번갈아** 녹화 (연속 50개 금지 — 조명·배터리 드리프트가 특정 상품에 편향되는 것 방지)
3. 매 에피소드 상품 위치·방향을 받침 안에서 조금씩 변화
4. pinky 위치도 도킹 잔여 오차 범위(±1~2cm, §5.2 실측값)로 흔들며 배치
5. 잘못된 칸 진열·파지 실패·어정쩡한 시연 = **그 자리에서 즉시 삭제**
6. 텔레오퍼레이션은 부드럽고 일관된 궤적으로 — 시연 품질이 곧 정책 품질
7. 데이터셋 이름에 상품·날짜 포함 (예: `shelfbot_v1_20260720`), 에피소드 메타에 상품 라벨

### 6.4 학습 (5090 서버)

- **모델: ACT** (LeRobot 기본 설정에서 시작, ~80M 파라미터)
- 근거: SO-ARM101 + 캠 2대 구성에서 가장 검증됨. 150 에피소드 학습 1~2시간 → 하루 2~3회 반복 실험 가능. Diffusion Policy는 이점 없이 추론 느림, VLA(SmolVLA/π0)는 데모 범위에 과함
- 파이프라인 (`train_remote.sh`): `rsync` 데이터 업로드 → ssh로 `lerobot train --policy.type=act ...` → 체크포인트 `rsync` 회수
- 서버 환경: **torch 2.7+ / cu128 먼저 설치 확인** — LeRobot 의존성이 구버전 torch를 끌어오면 5090에서 커널 미지원으로 즉사
- 학습 설정 시작점: LeRobot ACT 기본값 (chunk_size 100, 100k steps). 1차 학습 결과 보고 조정

### 6.5 평가·개선 루프

```
학습 → 상품당 10회 단독 평가 (도킹 완료 상태에서 PLACING만 실행)
  → 전체 80% 미만? → 실패 유형 분석:
      특정 상품만 낮음      → 그 상품 에피소드 +20 → 재학습
      인접 칸 오배치        → 칸 간격/시각 단서 보강 → 해당 데이터 재촬영
      파지 자체 실패        → 받침/그리퍼 점검, 시연 궤적 개선
  → 2회 반복해도 상품 구분 실패 → 플랜 B 전환
```

**플랜 B** (구분을 정책에서 제거): 탑뷰 HSV 색 검출(OpenCV 수십 줄)로 orchestrator가 상품 판별 → 상품별로 따로 학습한 "N칸에 놓기" 정책을 선택 실행. 정책 난이도 급감. 판별 코드는 미리 30분 투자로 짜 둘 가치 있음.

### 6.6 추론 (`run_policy.py`)

- 체크포인트 로드 → 캠 2대 + 관절 상태로 정책 스텝 루프 → 종료 조건(홈 자세 복귀 감지 or 최대 스텝) → 종료코드 0/1
- orchestrator가 서브프로세스로 호출, stdout을 로그로 흡수
- 핸드캠·탑뷰 프레임은 frame hub(§7.2)에서 공급 — 추론과 웹 스트림의 장치 경합 방지

### 7.2 Frame Hub (카메라 경합 해결)

핸드캠·탑뷰는 정책 추론·아루코 도킹·웹 스트림이 동시에 쓴다. USB 캠은 다중 오픈 불가 →
**각 캠당 리더 스레드 1개**가 프레임을 읽어 최신 프레임을 공유 버퍼에 유지, 소비자(도킹 루프·MJPEG 제너레이터·추론)는 버퍼에서 복사해 간다. `web/server.py`에 구현, 소비자별 락 최소화.

### 7.3 API

| 엔드포인트 | 메서드 | 동작 |
|---|---|---|
| `/start` | POST | READY → NAVIGATING. 이미 구동 중이면 409 |
| `/stop` | POST | 비상 정지 (§4.2) |
| `/retry` | POST | FAILED → 실패한 단계부터 재시도 |
| `/reset` | POST | DONE/FAILED → READY |
| `/stream/{top,hand,pinky}` | GET | MJPEG (multipart/x-mixed-replace) |
| `/map` | GET | OccupancyGrid → PNG + 메타(해상도·원점) JSON |
| `/ws` | WebSocket | 서버→클라 push: `{state, step_times, log_line, robot_pose, plan}` (pose/plan은 5Hz 스로틀) |

### 7.4 SLAM 내비 뷰 렌더

- 페이지 로드 시 `/map` 1회 → 캔버스 배경으로
- `/ws`의 robot_pose·plan을 지도 좌표→픽셀 변환해 로봇 삼각형·경로 폴리라인 갱신 (~100줄 JS)
- goal 지점 마커 고정 표시

### 7.5 웹 UI 신규 기능 (도착지/출발지 설정·파라미터 튜닝·장애물 대기·상태 LCD 송출)

| 기능 | API | 설명 |
|---|---|---|
| 도착지 설정 | `GET/POST /goal` | 지도 클릭 → 월드 좌표로 `POST /goal {x,y,yaw}`. orch는 `_goal_override`에 저장, NAVIGATING 진입 시 override 있으면 그것을, 없으면 `booth.yaml`의 `goal_pose` 사용 |
| 출발지 설정 | `POST /initialpose` | 지도 클릭 → `PoseWithCovarianceStamped`를 `topics.initialpose`(`/initialpose`)로 퍼블리시 (AMCL 초기화용) |
| 도킹 파라미터 튜닝 | `GET/POST /params` | `booth.yaml` `docking`의 게인·임계값을 런타임에만 조회/갱신(yaml 저장 안 함). DOCKING 진행 중 갱신 요청은 409 거부 |
| 물체감지 대기중 | (WS `pose_plan.obstacle`) | NAVIGATING 중 `/scan` 전방 ±`obstacle.fov_deg`/2, `obstacle.dist_m` 이내 장애물 감지 시 웹 배지·핑키 LCD에 표시 |
| 상태 LCD 송출 | (`topics.status_text`) | 상태 전이·장애물 플래그 변화 시 `std_msgs/String`을 TRANSIENT_LOCAL QoS로 퍼블리시 (READY→"대기", NAVIGATING→"가는중"/"물체감지 대기중", DOCKING·PLACING→"도착", DONE→"완료", FAILED→"오류") |

## 8. 통합 테스트·검증 계획 (기획서 4장 성공 기준과 1:1)

| 지표 | 목표 | 측정 절차 | 원자료 |
|---|---|---|---|
| 주행 도달 성공률 | 90%+ | 시작점→goal 20회, Nav2 SUCCEEDED 비율 | 사이클 로그 |
| 도달 위치 오차 | ±5cm | 위 20회에서 도킹 시작 전 아루코 pose로 오차 자동 기록 | docking 로그 |
| 진열 성공률 | 80%+ | 도킹 완료 상태에서 PLACING 20회 (상품 균등) | 육안 판정 + 로그 |
| 전체 시퀀스 성공률 | 70%+ | /start부터 무개입 20회 | 사이클 로그 |
| 사이클 타임 | 3분 이내 | 성공 사이클 10회 평균 | 사이클 로그 |

- 측정은 통합 완료 주에 하루 잡고 몰아서. 실패 사이클은 사유 태그(nav/dock/place)와 함께 기록 → 발표 자료의 분석 슬라이드 재료
- 시연 리허설: 발표 환경(프로젝터·와이파이)에서 최소 1회 전체 시연 — 현장 와이파이 불안정 대비 노트북 핫스팟 백업 플랜

## 9. 구현 순서·일정

| 순서 | 작업 | 산출물 | 완료 판정 |
|---|---|---|---|
| 1 | 부스 세팅 §3 (1~9) | 고정된 부스, 지도, booth.yaml | 지도에서 goal 주행 1회 성공 |

| 4 | 데이터 녹화 §6.3 | 150+ 에피소드 | 상품별 50+, 불량 0 |
| 5 | 학습·평가 루프 §6.4~6.5 | ACT 체크포인트 | 단독 진열 80%+ |
| 6 | `web/` | server.py, index.html | 4분할 화면 + 시작 버튼으로 1사이클 |

| 8 | 시연 영상·보고서·발표 | 3분 영상, 보고서, 슬라이드 | 리허설 1회 |

- 2·3은 병행 가능 (도킹은 이기문/강성준 중 1인, 상태머신 1인 식으로 분담)
- 4는 세팅 확정 후에만. 5는 5090에서 비동기로 돌므로 6과 병행
